# UIX 焦点：内容

当创建或修改可见的产品文案、标签、空状态、验证、状态或帮助文本时加载此文件。

## 产品文案规则

- 使用用户的产品语言和区域设置。
- 围绕用户任务和业务对象编写标签，而非实现结构。
- 避免在产品 UI 中使用内部交付、工具和工作流术语。
- 除非产品是开发者工具且用户任务需要，否则避免说明运行时命令、验证步骤或技术栈。
- 保持页面标题具体：命名产品区域或业务任务。
- 为每个业务对象使用一种词汇。不要在内部实体名称、API 名称和面向用户的标签之间交替。
- 在重复使用的产品中优先使用简洁的操作文案而非引导段落。

## 用户可见边界

这些短语属于实现说明，而非正常产品 UI：

```text
internal workflow id, generated artifact id, delivery phase, verification command,
localhost, Docker, Gradle, npm, Prisma, Spring Boot, SQLite,
validator term, generated by agent, build passed
```

仅当这些术语是用户的产品领域时，开发者工具是例外。

## 状态文案

- 加载：简短且作用域限于该区域。
- 空：说明业务状态和下一步操作。
- 验证：告诉用户修正什么以及在哪里。
- 错误：说明恢复方式，而非堆栈跟踪。
- 业务阻塞：陈述领域规则和受影响对象。
- 成功：确认变更了什么并在有用时显示新状态。

## 控件

- 按钮标签应是动词或明确的命令。
- 破坏性标签应命名破坏性操作。
- 仅图标控件需要可访问的标签。
- 当业务操作已知时避免使用如"Submit"之类的通用标签。

标签模式：

| 上下文 | 更好的标签 |
| --- | --- |
| 创建业务记录 | `Create request`、`Open account`、`Add supplier` |
| 破坏性操作 | `Close account`、`Delete draft`、`Cancel order` |
| 技术错误后重试 | `Retry`、`Reload list` |
| 业务阻塞 | `Resolve missing approval`、`Clear holdings first` |
| 详情导航 | `View details`、`Back to list` |

## 密集 UI

- 表格和徽章需要简短、一致的状态标签。
- 工具提示应澄清控件，而非包含移动用户无法访问的关键信息。
- 长帮助文本属于侧面板、详情部分或文档路由，而非每行内。

## Surface Copy Modes

根据用户的阅读任务选择文案模式：

| 界面 | 文案规则 |
| --- | --- |
| 工作台/数据 | 简短标签、明确状态、可操作的空/错误文本、紧凑帮助。 |
| 文档/散文 | 说明性层次结构、示例、标题、代码标签和可导航上下文。 |
| 营销/企业 | 价值主张、证明、差异化和转化语言。 |
| 消费者流程 | 熟悉的操作标签、信任/风险说明、确认和恢复。 |
| 开发者工具 | 仅当技术术语是产品主题时才允许使用。 |

不要将工作台的简洁应用于文档或营销，也不要将营销叙事放入操作屏幕。场景定义文案密度；产品语言定义术语。

## 本地化和长内容

- 在支持的最长区域设置和真实的业务名称、标识符、日期、金额和状态文本下测试标签。
- 将翻译保留在项目已建立的消息源中。当项目有区域系统时，不要在组件逻辑中放置重复的用户可见字符串。
- 根据区域策略保留产品名称、标识符、代码和单位。不要翻译用户必须复制或比较的值。
- 为长标签定义换行、截断、工具提示或详情视图行为；永远不要为了保持示例字符串在一行内而隐藏必需的操作。

## 文案证据

证据应引用变更的文件或屏幕来证明：

- 禁止的内部术语在产品 UI 中不存在。
- 空、错误、验证、成功和业务阻塞文案在这些状态在范围内时存在。
- 页面标题和操作标签使用业务语言。
- 长消息换行而不隐藏控件。
- 当文案或布局变更时记录检查的区域设置和最长内容案例。
